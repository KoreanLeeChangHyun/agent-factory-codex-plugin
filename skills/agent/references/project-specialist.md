# Project-specialized Work

## Identity

- A Specialist is bounded Work with a concrete project profile covering architecture,
  components, conventions, accepted decisions, workflow and relevant history.
- Graph: `Main -> project-specialized Work -> Verification` until an explicitly
  reviewed runtime change. No extra public Skill, role or MCP domain Agent.
- Specialization grants no self-verification, commits or Verification bypass.
  MCP capabilities support tasks without defining Specialist identity.

## Profile requirements

- Stable project/profile IDs; mission and bounded responsibility.
- Authoritative refreshable sources; included/excluded repositories, components and paths.
- Allowed capabilities/effects/scopes; project constraints and completion criteria.
- Provenance, version, freshness, invalidation and refresh conditions.
- Session continuity policy; memory grants no authority.

## Maintenance

1. Inspect current project evidence; distinguish stable conventions, changing state
   and unresolved Human choices.
2. Main binds exact target/scope/effect/capability/approval per task.
3. Create, refresh, retire or transfer through the resolved owning Agent/MCP runtime,
   preserving provenance.

- Do not manufacture expertise from summaries, accept stale memory as truth,
  infer capability authority or silently widen profiles.

## Unresolved design

- Do not invent schema, tool names, backend, Specialist cardinality policy,
  refresh/conflict rules, session compatibility, rollout priority, owner, deadline
  or deployment state. These remain Human-owned until resolved.
