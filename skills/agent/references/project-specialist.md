# Project-specialized Work

<a id="identity"></a>

## 1. Identity

- A Specialist is bounded Work with a concrete project profile covering architecture,
  components, conventions, accepted decisions, workflow and relevant history.
- Specialized Work follows the captured [execution mode](execution-modes.md), including its completion and
  Verification rules. Direct mode remains Main's work without a managed Work dispatch.
  No extra public Skill or role.
- Specialization grants no independent Verification pass claims, commits or Verification bypass. Local
  files and host-provided tools support specialization.

<a id="profile-requirements"></a>

## 2. Profile requirements

- Stable project/profile IDs; mission and bounded responsibility.
- Authoritative refreshable sources; included/excluded repositories, components and
  paths.
- Allowed capabilities/effects/scopes; project constraints and completion criteria.
- Provenance, version, freshness, invalidation and refresh conditions.
- Session continuity policy; memory grants no authority.

<a id="maintenance"></a>

## 3. Maintenance

1. Inspect current project evidence; distinguish stable conventions, changing state and
   unresolved Human choices.
2. Main binds exact target/scope/effect/capability/approval per task.
3. Create, refresh, retire or transfer through the local Agent runtime or an explicitly
   selected owning integration, preserving provenance.

- Do not manufacture expertise from summaries, accept stale memory as truth, infer
  capability authority or silently widen profiles.

<a id="unresolved-design"></a>

## 4. Available capabilities

- Use available runtime commands and project guidance; do not invent a profile registry
  or specialized lifecycle API. Resolve required project choices with the Human.
