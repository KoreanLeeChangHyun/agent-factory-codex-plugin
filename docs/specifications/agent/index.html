Agent Factory 에이전트

그래프

정확히 세 Agent 역할과 실행 그래프 하나를 갖는다.

Main -> Work -> Verification
          ^          |
          +-- fail --+
                     +-- pass -> END
                     +-- Human skip -> END
  • Main은 Human 대면 조율·결과 통합 역할이다.
  • Work는 제한 작업을 수행한다.
  • Verification은 최신 Work 결과를 독립 검증한다.
  • Verification 실패는 같은 Work에게 피드백을 돌려준다. 통과까지 Work·Verification을 반복한다.
  • Human은 다음 Verification 시작 전 언제든 skip 의도를 기록할 수 있다. 그 통제 의도는 현재 최초·수정 Work 턴 완료 뒤에만 적용되고 다음·추가 Verification 없이 END에 도달한다.

다른 역할·노드·경로를 추가하지 않는다. Main은 Work·Verification을 직접 수행하지 않고 Work는 자가 검증하지 않으며 Verification은 수리하지 않는다.

역할 프롬프트

역할 시스템 프롬프트 소스는 prompt/main.md, prompt/work.md, prompt/verification.md다. exec 호스팅에서는 런타임이 선택 파일을 검증·읽고 최초·재개 턴마다 전체 내용을 태그 역할 지시 블록으로 codex exec 표준 입력 요청에 주입한다. Agent Factory의 프롬프트 전송 계약이며 별도 플랫폼 시스템 채널 메시지를 주장하지 않는다. 유효 역할 ID는 main·work·verification뿐이다.

Human이 Codex CLI·exec 호스팅·VS Code 확장 중 무엇을 써도 Main은 같은 노드다. 진입 인터페이스·호스트이지 추가 역할이 아니다. 기본 진입점은 Codex CLI다. Main은 자식 작업 중에도 대화·정확한 활성 세션과 실행 상태를 유지하고 새 입력을 기존 작업에 연결한다. 새 입력은 이전 작업을 묵시 취소·포기하지 않는다. 명시적 Human 방향 전환은 실행·결과 상태를 보존하고 같은 그래프의 통제 전환으로 기록한다.

작업 분해와 체인 조율

Main은 인사·잡담·질문·브레인스토밍·작업 구체화를 제한 Work가 아닌 Human 대화로 취급한다. 작업을 정리·명확화·요약해 달라는 요청은 제안 작업만 준비하며 실행·위임을 승인하지 않는다. 제안 작업의 결과·범위·제약·완료 기준이 명확하고 그 뒤 Human이 실행·진행·위임을 명시 요청한 경우에만 위임한다. 두 조건이 모두 성립할 때까지 Main은 응답하거나 명확히 한 뒤 기다리며 관리 Agent·위임 요청·루프를 만들지 않는다.

그 위임 게이트가 충족된 뒤 Main은 실질적으로 나눌 수 있는 제한 작업을 조사하고 겹치는 저장소 경로·쓰기와 모든 공유 변경 자원을 고려해 의존성·실제 독립성을 판단한다. 유용하면 여러 독립 Work -> Verification 체인을 동시에 실행할 수 있다. 각 체인은 내부 순차로 유지하고 Work 완료 후에만 정확한 그 실행에 결속한 Verification을 시작한다. 의존되거나 겹치는 작업과 저장소 전체 통합은 순차 처리한다. 병렬 체인에는 서로 다른 Agent·루프·실행 ID, 제한 권위·역량 결속·입력을 부여하고 상태를 보존해 완료 결과를 의존 순서대로 통합한다.

분해·안전 배분은 Main의 조율 판단·책임이다. 런타임의 기계적 충돌 방지 보장·새 역할과 노드·최대 병렬화 요구가 아니다.

관리 세션

위임 Work·Verification은 scripts/exec.py로 시작하며 Main도 exec 호스팅할 수 있다. 정확한 Codex 세션 ID를 보존해 이후 같은 역할 세션을 재개한다. resume --last를 쓰거나 같은 세션에서 동시 턴을 실행하지 않는다.

운영 상태는 <runtime-home>/projects/<project-id>/agents/<agent-id>/에 둔다. 요청별 runs/<run-id>/에 요청·상태·하트비트·이벤트 스트림·응답 스키마·결과·역할 영수증을 둔다. 런타임 상태를 Skill·프로젝트 정보와 분리한다.

요청 본문·큰 맥락은 실행 디렉터리의 검증 파일로 전달한다. 경로 탈출·심볼릭 링크·예상 밖 파일 유형을 거부하고 런타임 파일을 원자 게시한다.

턴을 비동기 제출한다. 런타임은 영속 수락·프로세스 시작·하트비트·종료 완료를 구분한다. 하트비트는 감독 관찰이며 의미 진행 주장이 아니다.

Linux Worker 시작은 격리 역량을 협상한다. 필요한 명령·응답하는 사용자 관리자가 있으면 실행·시작 시도별 고유 결속 임시 systemd 서비스를 사용한다. Worker는 주 프로세스, Codex는 자식이며 Type=exec, 제어 그룹 종료·수거, 제출 프로세스의 안전하게 전달 가능한 환경, 제한 TERM→KILL 확대를 사용한다. 선택은 명령 기능·사용자 관리자·환경 전달 수단·cgroup-v2 구성원 인터페이스를 확인한다. 런타임은 시작 확인 전 또는 동시에 정확한 백엔드·불투명 격리 ID를 기록하고 조정·신호 전 결속을 조회한다. 취소 후 비어 있음은 서비스 상태·리더 PID만이 아닌 결속 제어 그룹 구성원으로 확인한다.

사용자 systemd가 없거나 쓸 수 없으면 기존 시작 장벽·비공개 세션과 프로세스 그룹·boot-ID/start-ticks PID 검증을 유지한다. 이 대체 경로는 식별자 불명에서 실패 처리하고 보수적인 오래된 실행·비재실행 동작을 유지하지만 자손 격리는 서비스 제어 그룹보다 약하다. Systemd는 협상되는 Linux 역량이며 보편 필수가 아니다. 격리 인터페이스는 미래 플랫폼 백엔드 경계이고 현재 Windows 지원을 주장하지 않는다. 이벤트·stderr 로그는 제한한다.

수락·시작·하트비트·턴 시간 제한은 별개다. 시작 전 재시도는 멱등적이어야 한다. 프로세스 시작 성공 뒤 시작 이벤트가 없으면 불명확하므로 자동 재실행하지 않는다. Human 권위 없이 비가역·외부 가시 작업을 재시도하지 않는다.

런타임 명령

홈 초기화·프로젝트 결속·단계별 레거시 이전은 references/home-runtime.md를 읽는다.

개별 관리 세션은 scripts/exec.py의 submit, send, status, result, inbox, list, cancel, reconcile을 사용한다.

Work·Verification 주기는 scripts/loop.py를 사용한다.

  • start: 최초 Work 제출.
  • reconcile: Work -> Verification, fail -> Work 또는 pass -> END 전환 하나 진행.
  • status: 루프 상태 조회.
  • skip --actor human --authorization-reference REF --decision-evidence TEXT: 다음 Verification 시작 전 명시 Human 생략 의도 기록.

근거 누락·비Human 생략은 실패한다. skip은 현재 Work 완료 후에만 다음·추가 Verification을 시작하지 않게 한다. 기록 자체는 전환·완료가 아니다. 관리 자식 실패·취소·Human 결정 요청은 통제 오류이며 그래프 완료가 아니다. Verification pass 또는 Work 완료 후 근거 있는 Human skip 적용만 END에 도달한다.

결과 통합과 커밋 게시

독립 Verification 통과 또는 Work 완료 후 근거 있는 Human skip 적용 뒤 Main이 승인된 Git 커밋을 제한 결과 통합·게시로 신속히 직접 수행한다. 이는 Work·Verification·새 역할·새 노드가 아니며 별도 커밋 Work 턴을 위임하지 않는다.

스테이징 전 Main은 최신 Work 결과·영수증, Verification 통과 영수증 또는 Human skip 근거, 현재 저장소 상태·차이를 조사한다. 해당 결과에 결속된 정확한 경로만 스테이징·커밋하고 무관한 dirty·untracked·generated·runtime 변경을 제외한다. Work·Verification은 커밋하지 않는다. 일반 커밋 권한은 push·amend·force·역사 변경·reset·restore·삭제·다른 저장소 게시와 변경을 뜻하지 않는다. 안전한 정확 스테이징·일반 커밋 실패 시 Main은 범위를 넓히지 않고 장애를 보고한다.

클라우드 보고와 검색

선택된 인증 클라우드 MCP가 공유 보고 저장·검색을 소유한다. 사용 전 agent-factory://reporting/cloud-guide와 현재 reporting_read·reporting_write·reporting_search 스키마를 읽는다. 문서 저장·검색과 필요한 영속 증거 업로드에는 Document 도구를 쓴다. 로컬 catalog 실행 파일과 스키마는 퇴역했다. 기존 .agent-factory/db.sqlite는 보존하며 새 도메인 작업 경로가 아니다. 백업·독립 가져오기 검증까지 데이터를 보존하며 코드 폐기가 데이터 삭제를 뜻하지 않는다.

로컬 exec.py는 프로세스·세션·실행 권위를, loop.py만 전환·실패 반환·Human skip·END 권위를 갖는다. 클라우드 작업·보고 상태는 관찰·의미 보고 투영이며 로컬 시작·재개·취소·완료 명령이 아니다. 기존 agent_run_submit을 보고 전송으로 쓰지 않는다. Work 작업 완료·Verification 실행 완료는 Verification 통과·그래프 END가 아니다. 계획 작업 상태와 백그라운드 작업은 별개다.

명시적 런타임 보고 설정·전달은 references/reporting.md를 읽는다. 연결·역량·수신자 결속 누락을 정직하게 보고하며 설정 계정을 추론하거나 테넌트·자격증명 권위를 선택하거나 로컬 MCP·공급자 서비스를 만들지 않는다. 기존 로컬 셸·파일 도구로 제한 Git·도구를 조사한다. 실행·발신함·확인·복구는 로컬에, 자격증명은 소유 권위에 둔다. 보고 실패는 로컬 실행을 재실행·인수하지 못한다.

영수증

완료 Work·Verification 실행은 result.md 옆에 검증된 receipt.json을 게시한다.

  • Work 영수증은 요청·변경 경로를 결속하며 수정 때 해결한 Verification 발견 ID도 나열한다.
  • Verification 영수증은 정확한 Work 실행·원래 요청에 결속하고 pass·fail 결정과 실행 가능한 수정 발견을 담는다. fail은 하나 이상 발견이 필요하며 pass는 발견이 없어야 한다.

관리 런타임 호출 전에 모든 자식 발송 의도·정확한 발송 튜플을 영속 저장한다. 중단 발송은 같은 ID로 조정하며 불명확한 확인에 대체 의도를 만들지 않는다.

모든 Verification 발송은 --verified-work-run-id를 제공한다. 실패 발견은 같은 Work 세션에, 다음 확인은 같은 Verification 세션에 전달한다.

MCP 역량 경계

MCP Tool 도메인은 외부 도구·연결의 논리 발견·생명주기를 소유하지만 준비 상태는 사용 권한이 아니다. Agent는 특정 역량을 Work·Verification 요청에 결속하고 실행 권위·영수증을 소유한다. MCP를 통해 선택한 호스트·플러그인·MCP 서버·프로젝트 매니페스트 권위를 유지하고 그 등록부·자격증명을 런타임 상태에 복사하지 않는다.

Main은 exec.py --capability-binding-file로 개별 관리 실행에 역량을 결속할 수 있다. loop.py start는 --work-capability-binding-file과 --verification-capability-binding-file을 분리해 최소 권한을 유지하며 한 역할 결속을 다른 역할에 전달하지 않는다. 엄격한 버전 문서는 고유 결속 1–32개를 포함한다. 각각 역량 ID·권위 종류와 참조·호출 경로·정확한 대상·허용 효과·허용 범위·null 가능한 승인 참조를 갖는다. 런타임은 알 수 없는 필드·한도를 검사하고 정규화 문서를 실행에 복사하며 해시를 불변 발송 튜플에 결속하고 상태에 정식 경로·해시를 노출한다. 자격증명·토큰 필드를 저장하지 않는다.

호출자 결속 파일은 파일·부모 심볼릭 링크를 해석·따라가지 않고 연다. 안전 순회 미지원·탈출 요소·일반 파일 아님·위험 부모·교체 경쟁·크기 초과는 발송 전에 실패한다. 마지막 요소를 비차단으로 연 뒤 일반 파일 디스크립터를 확인하므로 호출자 FIFO·소켓·장치가 런타임을 막지 못한다. 같은 열린 일반 파일에서 읽은 제한 바이트가 관리 실행에 정규화되는 바이트다.

결속이 있는 실행의 역할 영수증은 결속마다 순서 있는 capabilityOutcomes 항목 하나를 가져야 한다. 각 항목은 원래 요청 해시·정확한 실행 ID·역량 ID·권위·대상을 반복하고 succeeded, failed, unknown, not-invoked 중 하나만 기록한다. 영수증 검증은 정식 결속을 다시 읽고 해시를 확인하며 누락·재정렬·확대·대체 결과를 거부한다. MCP 준비 상태는 여전히 실행 권한이 아니다.

                     +-- pass -> END
                     +-- Human skip -> END

인사·잡담·질문·브레인스토밍·작업 구체화는 제한 Work가 아닌 Human 대화로 취급한다. 작업을 정리·명확화·요약해 달라는 요청은 제안 작업만 만들며 실행·위임을 승인하지 않는다. 다음 두 조건이 모두 충족될 때만 위임한다. 제안 작업에 명확한 결과·경계·제약·제외·완료 기준이 있고, 그 작업을 본 Human이 실행·진행·위임을 명시 요청해야 한다. 명확한 작업만으로는 실행 권위가 아니다. 두 조건이 성립할 때까지 직접 응답하고 요청대로 정리·명확화한 뒤 기다린다. 관리 Agent·위임 요청·루프를 만들지 않는다.

위임 게이트가 충족된 뒤 요청을 실질적으로 분리 가능한 제한 작업으로 조사하고 의존성·실제 독립성을 판단해 각 작업을 관리 Work Agent에 위임한다. 겹치는 저장소 경로·쓰기와 Git 인덱스·작업 트리, Agent·세션·루프·실행 식별자, DB·포트·외부 시스템을 포함한 모든 공유 변경 자원을 고려한다. 독립성 불명은 순차 처리·필요 Human 결정으로 해결하며 조용히 독립으로 취급하지 않는다. 유용하면 여러 독립 Work -> Verification 체인을 동시에 실행할 수 있다. 각 체인은 내부 순차로 유지하며 Work 완료 뒤 정확한 그 Work 실행에 결속한 Verification만 시작한다. 의존 작업·겹치는 쓰기·Git 커밋 같은 저장소 전체 통합·게시는 순차 처리한다. 병렬 체인마다 다른 Agent·루프·실행 ID, 제한 권위·역량 결속·입력을 부여한다. 모든 활성 체인을 추적하고 Human 대화를 계속하며 실행·결과 상태를 모두 보존한다. 작업을 잃거나 묵시 취소하지 않고 의존 순서로 통합한다.

작업 분해·안전 배분은 Main의 판단·책임이다. 런타임의 기계적 무충돌 보장을 주장하거나 병렬성을 최대화하거나 역할·노드를 추가하지 않는다. Work 완료마다 Human이 Verification 생략을 선택하지 않으면 최신 결과를 별도 관리 Verification에 위임한다.

적응형 Interview에는 Agent Factory convention Skill과 references/interview.md를 읽고 적용한다.

fail이면 발견을 같은 Work에 보내고 수정 결과를 같은 Verification에 보낸다. pass이면 최종 결과를 통합·보고한다. Human은 다음 Verification 시작 전 언제든 생략 의도를 기록할 수 있다. Human 행위자·권한 참조·결정 증거를 기록한다. 기록을 그래프 전환 아닌 통제 의도로 취급한다. 현재 최초·수정 Work 완료 후에만 적용되어 그래프를 끝내고 다음·추가 Verification을 막는다.

Verification 통과 또는 Work 완료 뒤 근거 있는 Human skip 적용 후 승인된 Git 커밋은 Main이 제한 결과 통합·게시로 직접 수행해야 한다. Work·Verification은 커밋하지 않는다. 별도 커밋 Work 턴·그래프 노드를 만들지 않는다. 최신 Work 결과·영수증, Verification 통과 영수증 또는 Human skip 증거, 현재 저장소 상태·차이를 조사한다. 해당 결과의 정확한 경로만 스테이징·커밋하고 무관한 dirty·untracked·generated·runtime 변경은 제외한다. 일반 커밋은 push·amend·force·역사 변경·reset·restore·삭제·다른 저장소 게시와 변경을 허용하지 않는다. 범위를 넓히지 말고 장애를 보고한다.

Work·Verification을 직접 수행하지 않는다. 역할·노드·경로를 추가하지 않는다. 제품·위험·범위 결정은 Human에게 남기고 파괴·외부 가시 작업의 명시 권위를 보존한다.

Work·Verification 실행 중 Human 메시지를 계속 받는다. 활성 Agent 세션·실행 식별자를 보존하고 새 메시지를 기존 작업의 추가·수정·상태 질문으로 연결한다. 이전 작업을 생략·묵시 취소·포기하지 않는다. Human이 명시 전환하면 실행·결과 상태를 보존하고 통제 전환을 기록한 뒤 같은 그래프 안에서 계속한다.

전달 범위·변경 경로·Verification 결과(pass 또는 skipped)·알려진 제약을 보고한다. 생략된 작업이 검증됐다고 주장하지 않는다.

Verification Agent

원래 Human 요청에 대해 최신 Work 결과를 독립 검증하고 pass 또는 fail 결정 하나만 반환한다.

회귀·제약 위반 없이 요청을 만족하는지 확인한다. Human이 승인한 검증 방법만 사용한다. 일반 구현 권위는 파괴·외부 가시 작업을 허용하지 않는다.

수정이 필요하면 구체적 실행 가능한 발견과 fail을 반환한다. 각 발견은 문제·증거·필요 수정을 식별하며 모두 Work 수정이 필요하다. 발견이 하나도 없을 때만 pass를 반환한다.

커밋하지 않는다. Git 커밋은 이 Verification 통과 또는 Work 완료 뒤 근거 있는 Human skip 적용 후 Main 소유 제한 결과 통합·게시다.

프로젝트 파일을 편집·수리하지 않는다. 다른 Agent를 조율하거나 새 그래프 경로를 추가하지 않는다. Human 소유 제품·위험·범위 결정을 하지 않는다.

홈 런타임 저장소

위치와 식별자

runtime/paths.py가 로컬 경로 해석을 소유한다. 실행 호스트는 기본 ~/.agent-factory 또는 명시적 절대 경로 AGENT_FACTORY_HOME을 사용한다. Codex는 자체 홈과 자격 증명을 유지한다. 코드 projectRoot는 정규 작업 트리 작업 디렉터리로 유지되고 runtimeRoot는 별도다. 새로운 체크아웃 .agent-factory 표식·런타임·문서 백엔드·카탈로그·심볼릭 링크 대체 경로를 만들지 않는다.

비공개 버전 관리 홈 레지스트리는 각 정규 작업 트리 경로에 무작위의 안정된 project-<32 hex> 식별자를 부여한다. 같은 원격 저장소라도 별도 복사본과 Git 작업 트리는 서로 다른 식별자를 받는다. projects/<project-id>/agents/<agent-id>/에 세션·실행·루프를 두며 각 실행이 자체 발신함을 소유한다. 초기화는 잠금·소유자 전용 디렉터리와 파일·한 번만 만드는 레이아웃 메타데이터를 사용한다. 안전하지 않은 링크·지원하지 않는 레이아웃 버전·모호한 결속은 실패 처리한다.

exec.py init --project-root PROJECT는 첫 제출 및 확장 연결과 같은 도우미로 명시적으로 초기화한다. location과 projects는 버전 있는 기계 판독 위치와 등록을 반환한다. list·기능 검사·상태 탐색은 없는 저장소를 초기화하거나 변경하지 않는다. 감독자·Worker·루프 자식·네이티브 브리지·보고 전송자는 해석된 홈/프로젝트 결속을 유지한다. 읽기 전용 역할은 Codex가 지원하는 이름 있는 권한 프로필을 사용한다. /는 읽을 수 있고 정확한 관리 실행 디렉터리만 쓸 수 있으며 샌드박스 도구의 네트워크를 끄고 작업 공간 샌드박스 플래그로 코드 루트를 넓히지 않는다. workspace-write 역할은 명시적인 코드 루트 동작을 유지한다. Linux에서 이 분할 정책은 레거시 Landlock 정책으로 의미를 유지하며 왕복할 수 없어 Codex의 bubblewrap 백엔드가 필요하다. 호스트가 bubblewrap 사용자 네임스페이스 설정을 거부하면 Codex는 실패 처리한다. 더 넓은 레거시 정책으로 바꾸지 않는다. 백엔드 협상은 https://github.com/openai/codex/blob/main/codex-rs/linux-sandbox/README.md 에, 현재 Codex 설정 계약은 https://learn.chatgpt.com/docs/config-file/config-reference 에 있다.

식별자를 유지하는 명시적 위치 변경에는 exec.py rebind --runtime-home HOME --project-id ID --from-root OLD --project-root NEW를 사용한다. 이전 레지스트리 결속이 일치해야 하고 새 코드 디렉터리는 존재하며 미등록이어야 한다. 활성 실행은 재결속을 막는다. 재결속은 별도 프로젝트를 병합하거나 충돌하는 이력을 선택하지 않는다. 명시적 재결속 뒤 클라이언트를 다시 시작한다. 이미 연결된 클라이언트는 고정된 결속을 유지하고 레지스트리 결속 변경 시 실패해야 한다.

설치와 연결

지원되는 설정 진입점은 python3 /absolute/installed/plugin/skills/agent/scripts/exec.py init --project-root /absolute/code/worktree다. 플러그인 체크아웃 밖에서도 작동하며 승인된 관리 설치/설정 흐름에서 사용할 수 있다. 기본 마켓플레이스 설치는 임의의 설치 후 명령을 실행하지 않는다. 매니페스트는 초기화 훅을 제공하지 않으며 플러그인 설치가 훅을 자동 신뢰하지 않는다. 캐시 버전 변경·재설치·설정된 자격 증명 변경은 런타임 초기화에 포함되지 않는다. VS Code 작업 공간 확장 호스트는 SSH/컨테이너 호스트를 포함해 자체 홈을 해석하며 UI 호스트의 홈은 관계없다. 한 연결은 검증된 결속과 파일 시스템 이벤트 서명을 캐시하고 초기화 실패는 캐시를 비운다.

결정적 레거시 이전

runtime/migration.py는 inventory·plan·copy-request·copy·verify-eligible·activate·retire를 제공한다. 각 레거시 상위/플러그인/확장/MCP 프로젝트를 별도 반복 --project-root로 전달하며 중첩 프로젝트가 하나의 식별자라고 추론하지 않는다. 계획은 전체 파일 목록·크기·SHA-256 해시·디렉터리 목록·홈/프로젝트 레지스트리 결속·정확한 운영 위치 매핑·잘못된 비활성 기록의 정직한 보관 전용 분류를 결속한다. copy-request는 Work가 복사하기 전에 선택한 독립 백업과 결정적 원본/투영 해시를 결속한다. 계획은 데이터이며 실행 가능한 모델 출력이 아니다.

복사는 원래 요청·결과·영수증·이벤트 및 기타 레거시 바이트를 홈 이전 보관소와 홈/원본 프로젝트 모두 밖의 독립 백업에 유지한다. Agent 런타임 기록만 별도 운영 투영을 받는다. 레거시 문서와 SQLite는 보관하며 로컬 도메인 백엔드로 승격하지 않는다. 추적된 Human 명세 저작 소스는 docs/specifications/<id>/에, 추적된 역사적 가공 문서 증거는 원래 바이트와 Git 이력을 유지하며 docs/archive/processed/에 둔다. 추적되지 않은 런타임·원시 비밀·자격 증명 캐시를 Git에 추가하지 않는다.

원본 변경·안전하지 않은 경로 탐색/링크/특수 파일·활성 상태 또는 검증 불가능한 부팅 ID/시작 틱 프로세스 식별자·채워진 격리 영역·점유 작성자 잠금·목적지 충돌은 이전을 거부한다. 복사는 의도를 저널에 기록하고 동일 재시도를 지원한다. 보관소·백업·투영·활성화 트리는 빈 디렉터리까지 포함한 전체 허용 목록으로 검사하며 외부 파일과 교체된 inode는 실패 처리한다. 운영 JSON 판독기는 존재하지 않는 선택적 출력 경로를 포함해 알려진 파일 시스템 위치 필드만 가장 긴 프로젝트 루트 결속 접두사로 해석한다. 역사적 요청 식별자·영수증 해시·세션/실행/루프 ID·보고 수신자·임의 페이로드 문자열·발신함 명령은 다시 쓰지 않는다. exec.py map-path --project-root PROJECT --path OLD_PATH는 전체 프로젝트 간 매니페스트로 정확한 역사적 증거 경로를 보관 경로와 바이트 해시로 해석하며 관리 프롬프트가 이 경로를 안내한다. 보관소는 불변 역사적 증거로 유지되며 잘못된 기록에 조작된 의미 완료를 부여하지 않는다.

verify-eligible은 결정적 바이트 적격성만 제공한다. 독립 Verification은 복사 상태·유효/무효 영수증·프로젝트 간 증거 매핑·정확한 세션 계속·그래프 pass/fail/skip·보고 복구를 검토해야 한다. 활성화는 실제 완료된 관리 Work와 Verification 상태 파일을 지목하는 버전 2 봉투만 받는다. 정규 실행/세션 소유권·정확한 요청/결과/응답/영수증 스키마와 해시·종료 이벤트·서로 다른 역할 세션·Verification의 엄격한 pass 영수증·정확한 계획/홈/백업/원본/투영 결속을 다시 검증한다. 선택한 JSON 키·파일명·결속되지 않은 추가 필드는 이 계약을 대신할 수 없다. 활성화는 복구 가능한 저널로 운영 투영을 게시하며 부분 게시는 복구까지 사용을 막는다. 원본 폐기에는 이미 승인된 정확한 원본 폐기 참조와 변경되지 않은 원본/보관소/백업/투영 증거가 추가로 필요하다. 각 재시도는 작성자 배제와 전체 허용 목록을 다시 검사하고 inode에 결속된 unlink/rmdir 의도 하나씩을 영속하며 외부 또는 교체된 원본/묘비 내용을 거부한다. 승인된 폐기에는 실제 검증 증거가 필요하며 새 권한 요청이 필요한 것은 아니다. Main이 제어를 이전하고 독립 검증이 폐기를 허용할 때까지 고정된 이전 부트스트랩 런타임과 그 활성 기록을 유지한다.

권위와 한계

이 저장소 계약은 클라우드 도메인 권위·두 Skill 식별자·Main -> Work -> Verification 그래프를 바꾸지 않는다. Work는 구현과 테스트를 작성하되 실행·Agent 조율·커밋·배포·물리적 전환을 하지 않는다. Verification 뒤 통합은 Main이 소유한다. 코드 변경이나 복사 성공은 물리적 이전·독립 수락·클라우드 가져오기·설치·배포를 입증하지 않는다.

로컬 실행과 클라우드 보고

소유권과 설정

exec.py는 로컬 프로세스·세션·실행 사실을, loop.py는 그래프를 소유한다. 클라우드 reporting_read, reporting_write, reporting_search는 실행이 아닌 공유 보고 저장·발견을 소유한다. 제공된 agent-factory://reporting/cloud-guide와 스키마를 읽는다. 개발 인계 위치 /tmp/af-cloud-migration-20260906/local-reporting-handoff.md는 개발 증거 위치이며 설치 의존성이 아니다.

보고는 exec.py --reporting-config로 명시적으로 선택하며 없으면 실행은 로컬에 남는다. loop.py start에서는 역할별 --work-reporting-config와 --verification-reporting-config를 구분해 사용하며 한 역할의 보고 설정을 다른 역할에 묵시적으로 전달하지 않는다. 실제 엔드포인트, 수신자·프로젝트·조직·Workspace·보고 사용자·클라우드 Agent 식별자와 자격증명 소유 참조를 기존 권위에서 확인한다. 테넌트를 조용히 고르거나 클라우드 Agent를 만들거나 범위를 올리지 않는다. 엔드포인트는 정확하고 인증되며 수신자에 결속돼야 한다. 설정·실행 상태에 자격증명을 넣지 않고 비밀은 저장소·런타임 데이터 밖의 소유 저장소에 둔다. 변화 중인 전송 내부를 호출자에게 복사하지 말고 설치된 런타임의 현재 설정 계약을 사용한다. 설정된 계정을 발명하거나 설정에서 실제 전달을 주장하지 않는다.

영속 연결과 전달

실제 Codex 세션 ID가 영속 저장된 뒤에만 각 실행을 새 클라우드 작업으로 등록한다. 정확한 프로젝트·로컬 Agent·실제 세션·실행·선택적 루프 식별자를 불변 runtime binding에 유지한다. 재개 세션의 새 실행은 새 작업 UUID를 받고 재연결·재시도는 원래 작업·결속·대상·보고 사용자를 유지한다.

네트워크 전송 전에 검증된 명령·영속 키·예상 리비전·비밀 없는 대상과 결속을 로컬 발신함에 원자 저장한다. 전달 완료 표시 전에 응답 확인을 저장한다. 확인 유실은 전달 불명이므로 자격증명 교체 후에도 현재 권한으로 같은 명령·키를 재전송한다. 대기 명령을 바꾸거나 새 키로 리비전·식별자 충돌을 우회하지 않는다. 현재 클라우드 상태를 읽고 실제 새 의도 이벤트는 별도로 조정한다. 원래 명령과 안전한 영수증을 복구용으로 보존한다.

기존 명시 명령 exec.py reporting-deliver --project-root PROJECT --agent AGENT --run-id RUN으로 해당 실행의 대기 보고를 조정·전달한다. AI 턴을 만들지 않으며 submit이나 기존 agent_run_submit을 호출하지 않는다. 네트워크 전달은 프로세스 감독·종료 밖에 있고 로컬 그래프 권위를 막거나 대체할 수 없다. 실패·거부·시간 초과·확인 불명·수신자 변경은 비밀 없는 진단과 함께 대기로 남는다. 로컬 exec·loop 경로와 확장 명령·배치 호환성을 유지하며 백그라운드 데몬이나 새 로컬 공급자 서비스가 필요하지 않다.

관찰은 의미 완료가 아니다

하트비트는 실제 관찰한 process_alive, process_exited 또는 unreachable 사실만 영속 증가 순번·후퇴하지 않는 관찰 시각·정확한 결속으로 보고한다. 수신 시각은 전달 신선도이지 관찰 신선도가 아니다. 관찰 누락·오래됨·프로세스 종료·반환 코드·연결 끊김에서 진행·실패·취소·의미 결과·그래프 END를 발명하지 않는다. 시계 편차를 우회하려 시각을 만들지 않는다.

의미 보고에는 검증된 명시적 종료 결과 증거와 해당 역할 영수증이 필요하다. 영속 의미 의도를 보존하고 실행을 다시 수행하지 않고 증거 포착·전달을 재시도한다. 정확한 결과와 검증 영수증 해시에 결속하며 변경·교체된 증거는 대기 실패로 남는다. 필요한 문서 증거는 자체 권한으로만 업로드한다. 자유 형식 요청·경로·환경·비밀·임의 결과와 영수증 본문은 보고 메타데이터가 아니다. Human 결정 결과는 입력 필요로 남고 런타임만의 실패는 통제 사실이며 만들어낸 의미 결과가 아니다.

클라우드 작업 상태를 읽고 의미·관찰·전달 신선도를 구분한다. 검색은 제한된 리터럴 발견 발췌이며 판정이 아니고 링크 내용을 가져오지 않는다. 클라우드 보고 완료는 로컬 Verification 통과를 증명하지 않는다. 로컬 검증 영수증·루프 상태가 그 권위를 유지한다. 계획 도구는 개발 작업을 설명하며 백그라운드 작업 실행 및 이 런타임 보고 흐름과 별개다.

배포 경계

남겨 둔 어댑터는 최소 로컬 런타임 의존성이며 클라우드 도메인 백엔드가 아니다. 계약·소스 존재는 서버 등록·마이그레이션·운영 자격증명·전송과 RLS 검증·배포·1–13단계 완료를 성립시키지 않는다. 대기 전달·복구 증거를 보이게 유지한다. 출처·데이터 폐기는 백업·독립 가져오기 검증과 필요한 정확한 삭제 권한을 기다린다.
